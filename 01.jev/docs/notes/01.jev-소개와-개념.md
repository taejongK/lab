# 01. Jev 소개와 개념

> 기준일 2026-10-09. 출처 표시 없는 서술은 TypeSafe 공식 블로그/문서 기준.
> **논문·기술 리포트·가중치는 아직 없다.** 아래의 "어떻게 동작하나"는 대부분 주장이거나 추론이다.

## 한 줄 정의

**Jev는 텍스트를 생성하지 않고, 정해진 선택지 위의 확률분포만 돌려주는 "판단 전용" 모델이다.**

```
unstructured state in  →  typed probabilistic decisions out
```

## 1. 왜 나왔나 — 문제 제기

TypeSafe의 출발점은 이 질문이다.

> "Models have been superhuman at chat for years, so where is all the automation?"

이들의 진단은 LLM이 **사람이 읽도록** 최적화됐다는 것이다. 그런데 자동화 파이프라인에서
LLM 출력을 소비하는 건 사람이 아니라 코드다. 코드는 다음 세 가지를 원한다.

1. **타입**: 문자열을 파싱하지 않고 바로 `if`에 넣을 수 있는 값
2. **속도와 비용**: 요청 한 건마다 수 초씩 기다리고 센트 단위로 돈을 낼 수는 없다
3. **신뢰도**: 이 답을 믿고 자동 처리할지, 사람에게 넘길지 정할 숫자

채팅 LLM은 셋 다 약하다. 그래서 **사람이 아니라 코드가 소비하는 모델**이라는 게 Jev다.

## 2. "System One"이라는 이름

Kahneman의 이중 처리 이론에서 따왔다.

| | System 1 | System 2 |
|---|---|---|
| 사람 | 빠르고 직관적인 즉답 | 느리고 단계적인 숙고 |
| AI 대응 | **Jev** — 한 번에 판정 | Reasoning LLM — 추론 체인을 생성 |

TypeSafe가 내세우는 멘탈 모델은 **"전문가가 리서치 없이 5초 안에 내릴 수 있는 판단"을 기계 규모로**이다.
설명이나 여러 단계의 추론이 필요한 판단은 처음부터 Jev가 맡을 일이 아니다.

## 3. 소프트웨어 안에서의 위치

| | 하는 일 |
|---|---|
| 코드 | 계산한다 (calculate) |
| **Jev** | **판단한다 (judge)** |
| Reasoning LLM | 추론하고 생성한다 (reason & generate) |

권장 구조에서 **제어 흐름은 코드가 쥐고**, Jev는 규칙으로는 안 되는 좁은 의미 판단만 공급한다.

```
애플리케이션 state
   ↓
결정론적 코드 (규칙·계산)
   ↓
Jev  ── 의미 판단 ──→  타입 값 + 확률분포 + confidence
   ↓
결정론적 코드 (confidence 임계값으로 분기)
   ├─ 높음 → 자동 처리
   ├─ 애매 → 사람 리뷰
   └─ 어려움 → Reasoning LLM
```

이 그림에서 Jev의 가치는 정확도보다 **confidence 숫자로 분기할 수 있다**는 데서 나온다.
그래서 이 스터디에서 제일 중요한 검증 포인트도 calibration이다 (§6).

## 4. 핵심 개념

### 4.1 입출력 계약

```
입력:  state      — 판단 근거가 되는 텍스트 또는 구조화된 객체 (하나)
       questions  — 이름 붙은 질문 여러 개. 각자 타입과 답의 공간을 미리 정의

출력:  질문마다
       - 타입 값 (선택지 중 하나 / yes-no / 척도 위치)
       - 전체 확률분포
       - confidence (0~1)
```

문자열은 한 글자도 생성하지 않는다. 그래서 **파싱 단계가 없다.**

### 4.2 세 가지 프리미티브

질문의 타입은 세 가지뿐이다 (docs 기준).

| 프리미티브 | 답의 공간 | 돌려주는 것 | 대표 용도 |
|---|---|---|---|
| **Noul** | {yes, no} | yes 확률 | 탐지, 정책 체크, 가드레일 |
| **Choice** | 직접 준 선택지 (최대 255개) | 고른 값 + 선택지별 확률 | 분류, 라우팅, 인텐트 |
| **Score** | 순서 있는 척도 (2~10단계) | 확률 가중 위치 | 심각도, 관련성, 품질 |

- Choice의 255개 상한은 공식 블로그에도 있다. 그 이상은 "각 후보를 독립적으로 점수 매긴 뒤
  명시적으로 고르는 2단계 시스템"으로 처리하라고 권한다.
- Score가 Choice와 다른 점은 **순서**다. "3단계 중 2"와 "3단계 중 3" 사이의 확률을 섞어
  연속적인 위치를 낼 수 있다.

```python
from typesafe_sdk import Choice, TypeSafeClient

with TypeSafeClient() as client:
    r = client.system_one(
        state={"document": "I was charged twice. Please fix this ASAP."},
        questions={
            "category": Choice(
                instructions="What is this ticket about?",
                criteria={"billing": None, "technical": None, "other": None},
            ),
        },
    )
print(r.choices["category"].choice)   # "billing"
```

### 4.3 병렬 평가 (parallel sampler)

공식 설명은 "새 모델 아키텍처, 최대 효율을 위한 parallel sampler"이고, sampler에 대해서는
"Parallel. Generates all outputs in a single query"라는 한 줄이 전부다.

이 문장이 말하는 건 두 가지다.

1. **디코딩 루프가 없다.** 일반 LLM은 토큰을 하나 뽑아 입력에 붙이고 다시 forward를 도는
   루프 때문에 느리다. Jev는 답을 한 번에 낸다. 그래서 응답 시간이 70~500ms다.
2. **한 요청 안의 질문들이 동시에, 서로 독립적으로 평가된다.** 같은 state를 공유하면서 질문만
   여러 개 붙이므로 질문을 늘려도 지연이 거의 늘지 않는다. 대신 질문 A의 답이 질문 B에
   영향을 줄 수 없다. 의존 관계가 필요하면 코드에서 직접 엮어야 한다.

> 실제 구조(백본, 파라미터 수, "parallel"이 정확히 뭔지)는 공개되지 않았다.
> "constrained decoding이나 diffusion 비슷한 판단 모델"이라는 건 외부 관찰자들의 추측이다.

### 4.4 타입 안전 — 무엇이 보장되고 무엇이 아닌가

답의 공간을 미리 정의하므로 **스키마를 벗어난 출력은 원리적으로 불가능하다.**
TypeSafe도 각주에서 이걸 솔직하게 인정한다.

> "Our number is not empirical. Schema matching is guaranteed,
>  thus we can confidently add 0% into the plots."

그러니 "환각 0%"는 측정한 결과가 아니라 **정의상 참인 명제**다. 구분해서 볼 필요가 있다.

| 오류 종류 | Jev에서 |
|---|---|
| 파싱 실패, 없는 레이블 출력 (스키마 오류) | 구조적으로 없음 ✅ |
| 선택지 안에서 틀린 것을 고름 (의미 오류) | **여전히 있음** ❌ |
| 정답이 선택지에 없는데도 자신 있게 고름 | **여전히 있음.** 막으려면 `none_of_the_above`를 직접 넣어야 함 ❌ |

### 4.5 Calibration과 RLCD

Jev의 진짜 세일즈 포인트는 타입 안전이 아니라 **확률이 정직하다**는 주장이다.

**Calibration**은 confidence가 실제 정답률과 맞는 성질이다.
confidence 0.8로 낸 예측들을 모았을 때 실제로 80% 정도 맞으면 calibrated다.

$$\mathbb{P}(\text{정답} \mid \text{conf} = p) = p$$

정확도와 calibration은 **서로 다른 축**이다. 95%를 맞히면서 늘 0.999라고 외치는 모델은
정확하지만 calibrated는 아니다. confidence로 자동화 게이트를 건다면 이쪽이 더 위험하다.

**RLCD (Reinforcement Learning for Calibrated Decisions)** 는 TypeSafe가 이 성질을 학습시켰다고
주장하는 방법이다. 다른 RL 계열과 비교하면 이렇다.

| 방법 | 무엇에 보상을 주나 |
|---|---|
| RLHF | 사람이 선호하는 텍스트 |
| RLVR | 검증 가능한 정답 |
| **RLCD** | **구조화된 결정 위에서 "epistemically honest"한 확률** |

공식 자료에 있는 RLCD 설명은 이 비교표 한 줄뿐이다. 손실 함수, 보상, 학습 데이터, ablation은
없고, 블로그 FAQ에 "학습 알고리즘은?"이라는 질문만 있고 답은 없다.
**reliability diagram도 공개되지 않았다.** calibration을 핵심으로 내세우면서 그 증거가 되는
그림을 안 낸 게 이 모델에서 가장 이상한 점이다.

## 5. 언제 쓰고, 언제 쓰지 말아야 하나

### 적합성 체크 (6문항)

1. 콘텐츠 생성이 아니라 의사결정인가?
2. 답의 공간을 미리 정의할 수 있는가?
3. 초점이 하나인 판단인가?
4. 필요한 맥락이 전부 state 안에 들어가는가?
5. 사람 전문가라면 빠르게 판단할 수 있는가?
6. 결과를 소프트웨어가 바로 소비하는가?

→ yes가 5~6개면 좋은 후보, 3~4개면 문제를 쪼갤 것, 0~2개면 도구를 잘못 고른 것이다.

### 맞는 일

- **분류 / 라우팅**: 티켓 카테고리, 인텐트, 워크플로 분기
- **탐지 / 가드레일**: 정책 위반, jailbreak
- **스코어링**: 심각도, 관련성, 품질
- **리랭킹**: RAG 후보 필터링
- **LLM-as-judge 대체**: eval 채점
- **대량 map**: 수백만 건에 좁은 판단 하나씩
- **실시간 루프**: 게임 루프 안에서 판정 (Doom 데모. 단, 이미지가 아니라 텍스트로 된 상태를 넣음)

### 안 맞는 일

- 텍스트 생성 전부 (요약, 이메일, 코드)
- 판단 근거 설명 → 감사가 필요한 규제 도메인에 불리
- 미리 정의하지 않은 카테고리
- 툴 호출, 외부 검색, 다단계 추론
- 이미지 등 비텍스트 입력

## 6. 열린 질문 — "새로운 모델인가, constrained decoding인가"

이 스터디의 중심 질문이다. 양쪽 주장을 정리하면 이렇다.

**회의론** (Sean Goedecke 등)
- 기존 LLM에 프롬프트를 채우고 **선택지 토큰들의 logit만 읽어 재정규화**하면 비슷한 걸 만들 수 있다.
  forward 1회라 빠르고, 타입 안전도 똑같이 "정의상" 성립한다.
- test-time reasoning이 없으니 지능에 천장이 있다.

**TypeSafe 쪽 차별점 주장**
- constrained decoding은 **토큰 수준에서 거르는 것**일 뿐이다. 그 확률은 텍스트에 대해 학습된
  분포를 조건화한 것이지, 결정 자체에 대해 학습된 적이 없다.
- RLCD는 **결정 위의 확률 자체를 calibration 목표로 학습**했다.

정리하면 **차이는 속도나 타입 안전이 아니라 calibration에만 있을 수 있다.**
그래서 검증도 정확도가 아니라 calibration에서 출발해야 한다.

- 같은 데이터로 constrained decoding 베이스라인과 Jev의 **ECE / reliability diagram 비교**
- **정답을 선택지에서 뺐을 때** confidence가 떨어지는가.
  베이스라인은 남은 후보끼리 재정규화하므로 자신 있게 지어낸다.
  RLCD가 진짜라면 Jev는 confidence가 내려가야 한다.

## 7. 용어 정리

| 용어 | 뜻 |
|---|---|
| System One Model | 생성 없이 타입이 정해진 판단만 내리는 모델 클래스. Jev가 첫 사례 |
| state | 판단의 근거가 되는 입력 (텍스트 또는 객체) |
| question | state에 대해 묻는, 타입이 정해진 질문. 한 요청에 여러 개 |
| Noul / Choice / Score | 질문 타입: yes-no / 선택지 / 순서 척도 |
| confidence | 0~1. 이 답을 얼마나 믿을지. 자동화 게이트의 기준값 |
| calibration | confidence와 실제 정답률이 일치하는 성질 |
| ECE | Expected Calibration Error. calibration이 얼마나 어긋났는지 나타내는 수치 |
| RLCD | TypeSafe가 주장하는 calibration 목적의 RL 학습법. 상세 비공개 |
| parallel sampler | 디코딩 루프 없이 모든 답을 한 번에 내는 방식이라는 주장. 상세 비공개 |
| constrained decoding | 일반 LLM의 출력을 허용된 토큰으로 제한하는 기법. Jev의 귀무가설 |
