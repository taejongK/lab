# 02. Jev를 따라 만든 오픈소스 모델들

> 기준일 2026-10-09. 각 저장소의 README·문서·HF 모델 카드만 근거로 했다.
> **모든 수치는 저자 자기 보고다.** 직접 돌려본 건 없다.
> Jev 비교 수치도 대부분 Jev를 직접 호출한 게 아니라 TypeSafe나 제3자가 공개한 결과를 인용한 것이다.

## 요약

- 출시 3주 만에 Jev 형태를 따라 한 오픈 구현이 **30개 이상** 나왔다 (9월 조사 때는 9개).
- 구현 방식은 크게 **세 갈래**로 나뉜다.
  1. **LLM logit readout**: 기존 LLM이 내는 선택지 토큰의 logit만 읽어서 재정규화한다. 학습이 없거나 LoRA 정도만 한다.
  2. **LLM 백본 + 학습한 decision head**: LM head 대신 후보마다 점수를 내는 pointer head나 set attention을 붙인다.
  3. **인코더 + head**: ModernBERT 같은 양방향 인코더에 head를 붙인다. 가장 빠르다.
- **`POST /v1/systemone` 호환**이 사실상 표준이 됐다. 공식 TypeSafe SDK에서 `base_url`만 바꾸면 그대로 쓸 수 있다고 하는 구현이 많다.
- **RLCD를 재현했다고 하는 곳은 Laya 하나**다 (GRPO 방식, proper scoring rule로 보상). Valen과 Dohnuts는 "실험적 RLCD"라고 부르고, decider는 별도의 RL calibration 단계가 있다.
  모두 TypeSafe의 실제 레시피가 아니라 **각자 추정한 버전**이다.
- calibration은 **사실상 전부 사후 temperature scaling**에 기대고 있다. 그리고 여러 저장소가 "temperature를 맞춘 분포 밖으로 가면 유지되지 않는다"고 스스로 적어 두었다.
- 커뮤니티 벤치마크가 생겼다: **JevBench** (공개 231문항 + 비공개 sealed 셋), **typed-decisions** (LocalLLaMA, 2,000문항), **Decision Index**.

## 2. 갈래별 정리

### 2.1 LLM logit readout — "그냥 constrained decoding"

9월 노트북(`baseline-qwen3-readout.ipynb`, git `932e704`)과 같은 계열이다.
**Jev가 constrained decoding의 리브랜딩이라는 귀무가설을 그대로 구현한 것**이라고 보면 된다.

| 프로젝트 | 학습 | 특징 |
|---|---|---|
| **SemIf** | 없음 | state를 한 번 prefill하고 질문마다 분기. 3090에서 21개 기준을 판정하는 데 1.0s (자동회귀 JSON은 5.3s) |
| **AnyJev** | 없음 / Tacit은 자기 증류 | 선택지 순서를 K번 돌려가며 평균해서 **위치 편향을 제거**하고, 레이블 prior를 나눠서 없앤다. 애매하면 일정 비율만 CoT로 넘김. arXiv 2610.00831 |
| **litjev** | 없음 | 레이블 글자가 아니라 **선택지 텍스트 전체의 logprob 합**을 읽는다. 기본 모델 Qwen3.8-27B |
| **jev-local** | 없음 | 후보별 평균 logprob. 스스로 "재현이 아니라 인터페이스 호환 베이스라인"이라고 함 |
| **rizzo-flow** | LoRA (soft CE) | 답 글자 logit만 읽음. 학습 후 ECE 0.349 → 0.112 |
| **Nimble** | LoRA | 한 토큰짜리 답 코드의 logit을 softmax. "하루 만에 만들었다"고 밝힘 |
| **decider** | CE 파인튜닝 + RL | A~Z, 두 글자 토큰까지 써서 255개 지원. RL 단계에서 log score로 **calibration을 직접 학습**한다고 함 (RL 코드는 비공개) |
| **jevos** | 파인튜닝 | LM head에서 '0'/'1' 두 행만 남김. Choice는 선택지마다 yes/no를 묻고 정규화 |
| **openjev** | 없음 | 영어·중국어. 질문마다 context를 다시 인코딩 (느림, M3에서 533ms) |
| **TypeLLM** | 없음 | ⚠️ Jev 복제가 아니라 일반 structured output 라이브러리. 자동회귀 생성 |

**이 갈래에서 알 수 있는 것**
- 학습 없이도 JevBench 공개셋에서 Jev와 비슷한 구간까지 간다. SemIf 4B는 0.845 vs 0.883이고, TypeLLM 27B는 thinking 없이 195/231이다.
- 이 갈래의 공통 약점은 **위치 편향**(선택지 순서에 따라 답이 바뀜)과 **255개 지원**이다.
  첫 토큰 충돌을 피하려면 대부분 26개 정도에서 막힌다. 255개까지 가는 건 두 글자 토큰을 쓴 decider 정도다.

### 2.2 LLM 백본 + 학습한 decision head

LM head를 버리고 **후보별 hidden state를 질문 위치의 hidden state와 비교**해 점수를 낸다.
9월 06 문서 §4의 "세 번째 길"이 실제로 여러 개 나온 셈이다.

| 프로젝트 | head | 비고 |
|---|---|---|
| **kev** | pointer head (`<decide>` 위치 ↔ 각 옵션의 `</opt>`) | Archer Hume의 "Jev's Architecture Unmasked"에서 설계를 가져왔다고 밝힘. 질문끼리는 attention mask로 격리 |
| **strands-decider** | pointer head (약 100만 파라미터) | kev와 같은 설계. 고정 슬롯 head는 "훨씬 나빴다" |
| **NanoJev** | set attention (Choice) / sigmoid (Noul) | 게임 데이터만 사용. RLCD 실험 문서는 있지만 "공식 레시피가 아니"라고 명시 |
| **Valen** | 2층 MLP-Mixer | 이미지·영상 입력. GRPO 방식의 실험적 RLCD (보상 = 정답 − confidence 오차²) |
| **Dohnuts** | candidate scorer + LoRA | Laya의 RLCD 구현을 따른다고 함. 가중치는 비상업 라이선스 |
| **CLM** | state·action을 따로 임베딩하는 contrastive 방식 | state와 action 임베딩을 각각 캐시. 6천만 개 Q&A로 사전학습, 3천만 개 hard negative, 100만 개 에이전트 궤적 |

**이 갈래에서 알 수 있는 것**
- 첫 토큰 충돌 문제가 원천적으로 없어서 후보 수 제약이 풀린다.
- 대가로 **zero-shot이 사라진다**. head가 난수에서 시작하기 때문에 학습 데이터가 반드시 필요하다.
- kev의 pointer head 설계는 Jev 내부 구조를 역추정한 글에서 왔다. Jev 실체에 대한 가설로 읽어볼 만하다.

### 2.3 인코더 + head — 가장 빠른 쪽

| 프로젝트 | 구조 | 비고 |
|---|---|---|
| **Laya** | ModernBERT-large + 2층 transformer head, 옵션마다 `[MASK]` 위치에서 점수 | **RLCD를 직접 구현했다고 주장하는 유일한 곳.** 보상은 proper scoring rule(log + spherical + RPS), REINFORCE에 그룹 평균 baseline. 다국어 라우터 포함 |
| **von** | ModernBERT-large, 옵션마다 `[MASK]` | v1.2부터 옵션 순서를 바꿔도 답이 안 바뀜. 단, JevBench에서는 크게 뒤짐 (27.5 vs 63.3) |
| **Verdict** | 118M 다국어 bi-encoder | conformal abstain. README에서 Laya에 진다고 스스로 밝힘 (0.71 vs 0.77) |

**이 갈래에서 알 수 있는 것**
- 지연 시간은 압도적이다. 수십 ms 수준이고, 노트북 CPU에서도 돈다.
- **zero-shot이 거의 안 된다.** Laya 베이스 체크포인트는 typed-decisions에서 0.362로 무작위(0.318) 수준이다.
  저자도 "zero-shot 판단 엔진이 아니라 특화시킬 빠른 베이스"라고 쓴다.
- Laya가 Jev를 이겼다는 숫자(0.766 vs 0.727)는 **그 벤치마크의 train split으로 파인튜닝한 결과**라서 공정 비교가 아니다.

### 2.4 초소형 / 처음부터 학습

| 프로젝트 | 크기 | 비고 |
|---|---|---|
| **jevlike** | 바이트 인코더 | 학습 라이브러리. CUA-S1-FORMS, jevbetter, jevlike-esp32가 여기서 파생 |
| **jevbetter** | n-gram 인코더 | jevlike와 같은 데이터로 비교: top-1 0.916 vs 0.873. 대신 처리량은 40 vs 4,608 menus/s |
| **minojev** | 54.7만 파라미터 | CPU에서 처음부터 학습. maze ECE 0.016 |
| **CUA-S1-FORMS** | 70.6만 파라미터 (2.8MB) | 폼 필드 판단 전용. 자기 eval에서 99.7% vs Jev 83.6% (자기 홈그라운드) |
| **jevlike-esp32** | — | ESP32 마이크로컨트롤러 펌웨어로 export |

좁은 태스크에서는 아주 작은 모델이 Jev를 이길 수 있다. 다만 이건 **Jev의 범용성과는 다른 얘기**다.

## 5. 이 스터디에 주는 시사점

1. **"constrained decoding 리브랜딩" 가설은 정확도 측면에서는 꽤 버틴다.**
   학습 없는 readout(SemIf, AnyJev, TypeLLM)이 JevBench 공개셋에서 Jev와 비슷한 구간에 있다.
   남은 차별점 후보는 역시 **calibration**과 **255개 후보 처리**다.
2. **calibration은 아무도 제대로 못 풀었다.** 대부분 사후 temperature 하나로 처리하고, 분포가 바뀌면 깨진다고 스스로 적었다.
   kev는 5% 오류 예산에서 자동 처리 비율이 0.52~0.69로 Jev의 0.70보다 낮다고 보고한다.
   → 다음 실험의 핵심 비교축으로 그대로 쓸 수 있다.
3. **RLCD 재현 시도는 Laya, Valen, Dohnuts, decider, NanoJev 정도다.** 공통 아이디어는 "proper scoring rule을 보상으로, 생성 없이 결정 logit을 샘플링"이다.
   9월 06 문서 §6의 예측(마스크를 통과시켜 결정 분포 위에서 학습)과 형태가 맞는다.
4. **직접 돌려볼 후보**
   - 귀무가설 쪽: **AnyJev** (학습 없음, 위치 편향 보정 포함). 9월 노트북의 개선판으로 쓸 수 있다.
   - head 쪽: **kev** 또는 **strands-decider**. pointer head는 Jev 구조에 대한 가장 구체적인 가설이다.
   - RLCD 쪽: **Laya**. 공개된 RLCD 구현 중 가장 완결된 것.
   - 셋 다 `/v1/systemone` 호환이거나 거의 호환이라 **같은 하네스로 비교**할 수 있다. ollaya로 한 번에 띄우는 것도 방법이다.
5. **벤치마크 숫자 읽을 때 주의할 것**
   - Jev 수치는 대부분 직접 호출이 아니라 공개 기록을 인용한 것이다.
   - train split으로 파인튜닝하고 같은 벤치에서 잰 경우가 있다 (Laya).
   - 체크포인트 선택에 평가 셋을 쓴 경우가 있다 (jevos).
   - JevBench는 버전(v1, v1.4, v1.5.2)과 셋(public / hard / sealed)마다 숫자가 다르다.

## 6. 상업적 사용 가능 여부 (라이선스)

> 2026-10-09에 GitHub와 HF 메타데이터로 확인했다. **법률 자문이 아니다.** 실제 제품에 넣기 전에는 각 LICENSE 원문을 직접 볼 것.

라이선스는 **네 겹**으로 봐야 한다: ① 코드, ② 공개 가중치, ③ 베이스 모델, ④ 학습 데이터.

**학습 데이터 쪽 회색지대**
- kev-4b/27b와 strands-decider의 학습 데이터에는 **`Yelp/yelp_review_full`** 이 들어 있다. kev에는 `amazon_reviews_multi_en`도 있다.
  - Yelp 데이터는 Yelp 자체 약관(`yelp-licence`)을 따른다.
  - Amazon Multilingual Reviews는 원본이 비상업 연구용 라이선스로 알려져 있다. HF 재업로드본은 Apache로 태깅돼 있지만 신뢰하기 어렵다.
- 비상업 데이터로 학습한 가중치를 상업적으로 써도 되는지는 **법적으로 정리되지 않은 문제**다. 보수적으로 가려면 이런 데이터가 없는 모델(Laya, decider, von, AnyJev, CLM)을 우선한다.
- **Jev 출력으로 증류**했다면 TypeSafe 약관 문제가 생길 수 있다. 주요 프로젝트(kev, decider, Nimble, rizzo-flow)는 모두 "Jev 출력을 쓰지 않았다"고 명시한다.
  TypeSafe 사이트 약관(2026-09-19 갱신)에는 경쟁 모델 학습을 금지하는 조항이 보이지 않았다. 다만 API 이용약관이 따로 있는지는 확인하지 못했다.
