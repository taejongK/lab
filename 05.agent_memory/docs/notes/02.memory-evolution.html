0. 출발점

먼저 알아 둘 용어 7개

LLM
대규모 언어 모델. 글을 읽고 그 다음에 올 글을 이어 쓰는 모델이다. ChatGPT, Claude 같은 것.
프롬프트
LLM에게 한 번에 보내는 글 전체. 지시문, 참고 자료, 질문이 모두 여기에 들어간다.
토큰
LLM이 글을 세는 단위. 글을 단어나 글자 조각으로 잘게 쪼갠 것이다. 길이 한도와 사용 요금이 모두 토큰 수로 계산된다 (일반 설명).
컨텍스트 윈도우
LLM이 한 번에 읽을 수 있는 토큰의 최대 양. 이 문서에서는 "책상"이라고 부른다.
에이전트
LLM이 혼자 답만 쓰는 게 아니라, 도구를 골라 쓰면서 생각 → 행동 → 결과 확인을 여러 번 반복하는 프로그램.
도구 호출
LLM이 search("수령일") 같은 "도구 사용 요청" 글을 출력하면, 프로그램이 그걸 실제로 실행하고 결과를 다시 프롬프트에 붙여 주는 것. LLM이 직접 DB를 만지는 게 아니다 (일반 설명, 3단계에서 그림으로).
가중치
모델이 학습으로 얻은 내부 숫자들. 이것을 바꾸면 모델의 "습관"이 바뀐다. 대부분의 메모리 방식은 가중치를 건드리지 않고 프롬프트에 넣는 글만 바꾼다.
임베딩·RAG(2단계), 강화학습(4단계)은 처음 나오는 곳에서 설명한다.

LLM은 "기억"이 없다

LLM은 프롬프트 하나를 받으면 답 하나를 내고 끝난다. 다음 질문을 받았을 때 앞의 대화를 기억하는 장치는 모델 안에 없다. 채팅창에서 대화가 이어지는 것처럼 느껴지는 이유는, 프로그램이 지난 대화를 매번 프롬프트에 다시 붙여서 보내기 때문이다.

LLM은 본질적으로 상태가 없고, 제한된 컨텍스트 윈도우에 묶여 있다. 원문: "they remain fundamentally stateless, constrained by limited context windows" — Memory-R1

그래서 LLM은 책상 위에 펼쳐 둔 것만 보고 답할 수 있다. 책상 크기에는 한계가 있고, 책상이 어지러울수록 중요한 걸 놓친다. 에이전트 메모리 연구는 모두 한 질문에 대한 답이다.

핵심 질문 책상은 좁은데 기억할 것은 계속 늘어난다. 무엇을, 언제, 누가 책상 위에 올려야 하나?

큰 그림: "누가 결정하나"가 옮겨 간 역사

이 문서 내내 쓸 예시

온라인 쇼핑몰 고객센터 챗봇이 아래 질문을 받았다고 하자. 모든 단계를 이 질문 하나로 비교한다.

고객 질문 (11월 2일) "지난주에 산 운동화가 작아요. 270으로 교환돼요?"

챗봇이 제대로 답하려면 두 가지를 알아야 한다.

  • 규정: "교환은 상품 수령 후 7일 이내, 착용하지 않은 경우만 가능" (규정집 어딘가에 있음)
  • 이 고객의 기록: "10/29 주문 #A17 수령 완료" (수천 건의 과거 상담·배송 기록 어딘가에 있음)

정답: 10/29 + 7일 = 11/5까지이므로 교환 가능(미착용이면). 수령일을 모르면 판단할 수 없다는 점이 포인트다.

순서에 대한 주의 4단계는 "개념의 발전 순서"다. 실제 논문은 시간상 겹친다. 2023년 봄에 검색형 메모리(MemoryBank)와 에이전트형 기억(Reflexion, Voyager)이 거의 동시에 나왔다. 그래도 2023 → 2025로 갈수록 결정 권한이 "코드 → LLM → 학습"으로 옮겨 가는 흐름은 뚜렷하다. 최근 서베이도 메모리의 발전을 저장 → 반성 → 경험 3단계로 정리한다 (From Storage to Experience).

1단계 통째로 넣기

가장 단순한 방법이다. 지시문, 규정 문서, 지난 대화 기록을 전부 프롬프트에 이어 붙여 보낸다. 검색도 정리도 없다. 아래 애니메이션을 "다음"을 눌러 한 단계씩 보자.

애니메이션 1 · 책상(컨텍스트 윈도우)이 차오르는 모습

장점

  • 정보 누락이 없다. 모든 게 책상 위에 있으니 "검색이 못 찾아서" 틀리는 일이 없다.
  • 만들기 쉽다. 저장소도 검색기도 필요 없다.
  • 그래서 다른 방법을 평가할 때 기준선으로 자주 쓴다. Mem0 논문도 "대화 기록 전체를 처리하는 full-context 방식"을 비교 대상으로 넣었다 (Mem0).

한계 (애니메이션의 마지막 세 장면)

문제쉬운 설명근거
① 책상 크기 한계한도를 넘는 자료는 아예 못 넣는다.LLM은 "제한된 컨텍스트 윈도우"에 묶여 있다 — MemGPT
② 길수록 비싸고 느리다질문 하나마다 전체를 처음부터 다시 읽는다.모든 과거 턴을 붙이는 방식은 메모리가 끝없이 커지고 계산 비용이 늘어난다 — MEM1. Mem0는 이 방식 대비 응답 지연(느린 쪽 5% 기준)을 91% 줄이고 토큰 비용을 90% 넘게 아꼈다고 보고 — Mem0
③ 길수록 오히려 놓친다넣었다고 다 보는 게 아니다. 글이 길어지면 회상 능력이 떨어진다.장기 대화에서 상용 챗봇과 긴 컨텍스트 LLM의 정확도가 30% 떨어짐 — LongMemEval. 토큰이 많아질수록 정보를 정확히 떠올리는 능력이 떨어지는 현상("context rot")이 있고, 그래서 컨텍스트는 "늘릴수록 효과가 줄어드는 한정 자원"이다 — Anthropic 엔지니어링 글
④ 정리가 안 된다날것의 기록만 쌓이고 "이 고객은 어떤 사람인가" 같은 요약은 생기지 않는다.긴 컨텍스트나 RAG를 써도 아주 긴 대화에서는 "여전히 사람보다 크게 뒤처진다" — LoCoMo
그래도 여전히 쓸모 있다 자료가 작고(예: 수십 쪽 규정집), 잘 바뀌지 않고, 대화가 짧다면 통째로 넣기가 가장 정확하고 단순할 수 있다. Claude Code도 CLAUDE.md는 처음부터 그냥 넣는다 (Anthropic 엔지니어링 글). 메모리 구조는 복잡할수록 좋은 게 아니다.

2단계 검색해서 넣기 (RAG)

아이디어

책상에 전부 올리지 말고 질문과 관련 있는 것만 골라서 올리자. 자료는 책상 밖 "서랍"(외부 저장소)에 넣어 두고, 질문이 오면 프로그램이 서랍을 검색해 상위 몇 개를 꺼내 준다. 이것이 RAG(Retrieval-Augmented Generation, 검색으로 보강한 생성)다.

새 용어 3개

청크
긴 문서를 몇 문장 단위로 자른 조각.
임베딩
글 조각을 "의미 좌표"(숫자 목록)로 바꾸는 것. 뜻이 비슷한 글은 가까운 좌표에 찍힌다. 실제로는 수백~수천 차원이지만, 아래 그림에서는 2차원 지도로 그렸다. 이 좌표들을 모아 둔 저장소를 벡터 DB(벡터 저장소)라고 한다 (일반 설명).
top-k
질문 좌표에서 가장 가까운 조각 k개만 고르는 것. Mem0 논문이 RAG를 "청크 크기와 k값을 바꿔 가며" 비교한 것처럼, 청크 크기와 k가 RAG의 대표 조절 손잡이다 (Mem0).
애니메이션 2 · 자르기 → 의미 지도 → 가까운 k개 고르기
여기서 가장 중요한 점 2단계에서 무엇을 꺼낼지 결정하는 건 LLM이 아니라 검색 코드(거리 계산)다. LLM은 받은 조각만 보고 답한다. 받은 조각이 틀렸거나 부족해도 LLM은 "다시 찾아볼게"라고 할 수 없다. 애니메이션에서 수령일 기록을 놓친 이유가 이것이다.

RAG의 한계: 논문들이 지적한 것

한계쉬운 설명근거
질문이 명확해야 한다"이 소설의 주제가 뭐야?"처럼 답이 어느 조각에 있는지 드러나지 않는 질문은 검색이 어렵다.기존 RAG는 질문이 명시적이고 지식이 잘 정리돼 있다는 두 가지를 전제한다 — MemoRAG
조각끼리 연결을 모른다여러 조각을 이어야 답이 나오는 질문(다중 홉: 한 번에 못 가고 여러 번 건너가야 하는 질문)에 약하다. 예시 질문도 "주문 → 수령일"과 "상품 → 교환 규정"을 이어야 한다.벡터 검색에 의존하면 사람 기억처럼 서로 연결된 기억을 흉내 내기 어렵다 — HippoRAG 2
계속 들어오는 새 경험을 못 엮는다새 정보를 기존 지식과 엮어 정리하지 못한다.RAG를 써도 많은 양의 새 경험을 효율적으로 통합하기 어렵다 — HippoRAG
바뀌는 정보에 약하다"예전엔 260이었는데 지금은 270"처럼 변하는 정보를 다루지 못한다.RAG는 "정적인 문서 검색에 한정"된다 — Zep
비슷하다고 유용한 건 아니다애니메이션의 "환불 규정"처럼 뜻은 비슷하지만 쓸모없는 조각이 뽑힌다.수동적인 의미 매칭은 잡음을 자주 가져온다 — MemRL
규칙이 고정돼 있다무엇을 저장·검색할지가 사람이 정한 규칙에 묶여 있다.기존 파이프라인은 정적이고 경험칙에 의존한다 — Memory-R1

RAG 안에서의 개선: 연결 구조를 더하기

"조각끼리 연결을 모른다"는 문제를 풀려고, 조각을 점(사실)과 선(관계)으로 된 지도, 즉 지식 그래프로 만들고 그 선을 따라 검색하는 방법이 나왔다.

선을 따라 두 번 건너가면(다중 홉) 필요한 두 정보에 모두 닿는다.

  • HippoRAG (2024-05): 뇌의 해마가 기억을 색인하는 방식에서 착안해 LLM + 지식 그래프로 연결을 따라간다. 다중 홉 질문에서 기존 RAG보다 최대 20% 좋았다고 보고.
  • HippoRAG 2 (2025-02): 그래프를 붙이면 단순 사실 질문 성능이 떨어지던 문제를 고쳤다. 부제가 "From RAG to Memory"(RAG에서 메모리로)다.
  • LongMemEval (2024-10): 메모리 설계를 색인 → 검색 → 읽기 3단계로 나눠 각각 개선했다. RAG를 설계할 때 좋은 틀이다.
더 보기: RAG를 "기억"으로 쓰기 시작한 2023년 연구 5개
연구새로 더한 아이디어
Generative Agents (2023-04)가상 마을 주민 25명이 경험을 전부 기록하고, 시간이 지나며 상위 수준의 반성으로 합성하고, 필요할 때 검색해 다음 계획을 세운다. 날것의 기록 위에 "요약된 생각"을 한 층 더 쌓았다.
MemoryBank (2023-05)사람의 망각 곡선(에빙하우스)처럼, 시간이 지나고 덜 중요한 기억은 흐려지고 중요한 기억은 강화된다. "잊기"를 설계에 넣은 대표 사례.
SCM (2023-04)"언제·어떻게 기억을 쓸지"를 결정하는 메모리 컨트롤러를 따로 둔다. 3단계로 가는 다리.
RET-LLM (2023-05)글 조각 대신 "주문#A17 - 수령일 - 10/29" 같은 세 칸짜리(삼중항) 구조로 저장한다. 갱신과 해석이 쉽다.
ChatDB (2023-06)LLM이 데이터베이스 질의어(SQL)를 써서 표 형태 DB를 읽고 쓴다. 정확한 값이 필요한 다단계 추론에 유리.

그 밖에 MemoRAG(2024-09)는 긴 자료 전체의 요약 기억을 먼저 만들고, 초안 답변을 단서로 삼아 검색한다.

2단계 정리 RAG는 "책상 크기" 문제를 풀었다. 하지만 무엇을 꺼낼지, 무엇을 저장할지, 언제 고칠지를 정해진 코드가 결정해서 상황에 맞춰 움직이지 못한다. 다음 단계는 이 결정을 LLM에게 넘긴다.

3단계 에이전틱 메모리 (LLM이 직접 관리)

무엇이 달라졌나

에이전틱 메모리에서는 LLM 자신이 메모리를 다루는 행동을 고른다. 찾을지 말지, 무엇을 열지, 무엇을 새로 적을지, 무엇을 고치거나 지울지를 LLM이 판단하고 도구 호출로 실행한다.

CoALA는 언어 에이전트를 "여러 메모리 부품"과 "그 메모리와 바깥 환경을 다루는 정해진 행동 목록"으로 설명한다. 즉 메모리를 읽고 쓰는 것도 에이전트의 행동 중 하나다. 원문: "modular memory components, a structured action space to interact with internal memory and external environments" — CoALA
실무에서도 흐름이 같다. 답하기 전에 임베딩 검색으로 미리 골라 넣던 방식에서, 에이전트가 파일 경로 같은 가벼운 "주소"만 들고 있다가 필요한 순간에 도구로 불러오는 "그때그때(just in time)" 방식으로 옮겨 가고 있다. 원문: "embedding-based pre-inference time retrieval" → "just in time" context strategies — Anthropic 엔지니어링 글

도구 호출은 실제로 이렇게 일어난다

LLM이 글을 출력
답 대신 search("수령일")이라는 글을 쓴다. "이 도구를 이 값으로 써 줘"라는 요청이다.
프로그램이 실행
에이전트 프로그램이 그 글을 읽고, 실제로 메모리 저장소를 검색한다.
결과를 책상에 붙임
검색 결과 "10/29 수령 완료"를 프롬프트 뒤에 붙여 LLM을 다시 부른다. LLM은 결과를 보고 다음 행동을 고른다.

이 세 칸이 한 번의 "도구 호출"이고, 에이전트는 필요한 만큼 반복한다(일반 설명). 2단계와 비교하면, 검색어와 검색 시점을 LLM이 정한다는 점이 다르다.

3-1. 메모리를 운영체제처럼: MemGPT (2023-10)

에이전틱 메모리의 대표 출발점이다. 컴퓨터는 작고 빠른 메모리(RAM)와 크고 느린 저장 장치(디스크) 사이에서 데이터를 옮겨 "메모리가 큰 것처럼" 보이게 한다. MemGPT는 같은 원리로 LLM이 여러 메모리 계층 사이에서 정보를 옮기며 좁은 책상 너머의 정보를 다룬다.

운영체제의 계층형 메모리에서 착안한 "가상 컨텍스트 관리"로, 여러 메모리 계층을 관리해 제한된 컨텍스트 안에서 더 긴 맥락을 제공한다. 원문: "virtual context management ... a system that intelligently manages different memory tiers" — MemGPT
  • 비유: 책상 = RAM, 서랍 = 디스크. 무엇을 책상에 올리고 서랍으로 내릴지를 LLM이 정한다.
  • MemGPT 팀이 만든 Letta는 지금 "에이전트의 메모리는 에이전트가 배우면서 직접 편집한다"고 설명한다 (Letta docs).
  • 같은 비유를 이어받은 후속작: MemoryOS(단기·중기·장기 3계층), MemOS.

3-2. 쓰기와 정리도 LLM이: 추출·통합·연결

2단계는 원문을 그대로 잘라 넣었다. 3단계에서는 LLM이 대화에서 기억할 만한 것을 뽑고, 기존 기억과 합치고, 서로 연결한다. 예를 들어 상담 대화 전체 대신 "이 고객 발 사이즈 270" 한 줄만 남긴다.

서베이 From Storage to Experience는 이 흐름을 저장(기록 보존) → 반성(기록 다듬기) → 경험(기록에서 요령 추상화)으로 정리하고, Agent Memory in the Second Half는 메모리가 에이전트가 스스로 발전하는 기반이 되고 있다고 본다.

3단계의 새 문제

  • LLM이 잘못 쓰면 메모리가 오염된다. 틀린 사실을 저장하거나 맞는 기억을 지울 수 있다.
  • 규칙(프롬프트)에 기댄다. "언제 무엇을 저장하라"를 사람이 프롬프트로 정해 준다. 메모리가 복잡해질수록 LLM은 무엇을 저장하고, 어떻게 정리하고, 언제 고칠지 판단하기 어려워한다 — Mem-α
  • 모든 능력을 갖춘 방법은 아직 없다. 정확히 찾기·쓰면서 배우기·긴 흐름 이해·골라서 잊기 네 가지를 시험했더니 현재 방법들은 넷 다 해내지 못했다 — MemoryAgentBench
  • 느려진다. 애니메이션 3에서 보듯 LLM 호출이 여러 번 일어난다(일반 설명).

4단계 정리 최근 서베이는 메모리 연산을 다루는 정책 자체를 학습하는 흐름을 짚는다 (Agent Memory in the Second Half). 다만 훈련 데이터와 모델 훈련이 필요해서, API로만 모델을 쓰는 서비스는 바로 적용하기 어렵다. 실서비스는 대부분 아직 3단계에 있다 (설계 비교 보고서).

같은 질문, 네 가지 방식

지금까지 본 네 단계를 예시 질문 하나로 나란히 놓으면, 결국 차이는 "책상 위에 무엇이 올라가는가"이고 그걸 "누가 결정하는가"다.

자주 헷갈리는 것

Q. 에이전틱 메모리가 RAG보다 항상 좋은가?

아니다. 단계가 올라갈수록 유연해지지만 LLM 호출이 늘어 느려지고, 잘못 쓰면 메모리가 오염된다. 자료가 작고 고정적이면 1단계가, 큰 문서에서 사실을 찾는 일이면 2단계가 나을 수 있다. 실서비스는 섞어 쓴다. Claude Code는 CLAUDE.md를 처음부터 넣고(1단계), 나머지는 에이전트가 파일 도구로 필요할 때 찾아 읽는(3단계) 혼합 방식이다 (Anthropic 엔지니어링 글).

Q. RAG와 "메모리"는 같은 말인가?

겹치지만 다르다. 서베이 Memory in the Age of AI Agents는 에이전트 메모리를 RAG·컨텍스트 엔지니어링과 구분하는 것부터 시작한다. 간단히 말해 RAG는 주로 "이미 있는 자료를 읽는 방법"이고, 에이전트 메모리는 경험하면서 쓰고, 고치고, 잊는 것까지 포함한다.

Q. "에이전틱"의 핵심은?

메모리 연산(찾기·읽기·쓰기·수정·삭제)을 LLM이 행동으로 고른다는 것이다. 저장소가 벡터 DB든 파일이든 그래프든 상관없다. A-MEM은 이를 "에이전트 주도 의사결정의 유연함"이라고 표현한다 (A-MEM).

Q. 그럼 CS 챗봇에는?

이 폴더의 CS 챗봇 메모리 구조 보고서 참고. 규정은 1단계(그대로 넣기) 또는 3단계의 "목차 보고 열기", 과거 상담 기록은 3-3의 경험 메모리(사례 카드·플레이북)가 맞는 자리다.

부록

곁가지 · 모델 안에 기억을 넣기

지금까지는 전부 "모델 밖"(책상과 서랍)에 기억을 두는 방식이었다. 다른 갈래로 모델 내부에 기억 장치를 넣는 연구도 있다.

  • LongMem (2023-06): 원래 모델은 그대로 두고, 별도 작은 네트워크가 과거 문맥을 저장해 두고 꺼내 읽는다.
  • MemoryLLM (2024-02): 모델 내부 숫자 공간에 고정 크기 메모리 칸을 두고 새 지식으로 스스로 갱신한다. 후속작 M+ (2025-02)는 이를 더 큰 장기 메모리로 늘렸다(제목 기준).
  • Titans (2024-12): 모델이 글을 읽는 기본 장치(어텐션)를 "단기 기억"으로, 새로 붙인 신경망 메모리를 "장기 기억"으로 보고 둘을 결합했다. 200만 토큰 이상으로 확장.

검색 없이 기억이 모델에 녹아든다는 장점이 있지만, 무엇을 기억하는지 사람이 들여다보거나 고치기 어렵다(일반 설명).
