# 01. 에이전트 메모리 주요 아키텍처 패턴 (2025~2026)

- 작성일: 2026-10-27
- 목적: 최근 가장 주목받는 메모리 방식을 큰 카테고리 6개로 나누고, 대표 방법론이 **어떤 구성요소로 어떻게 연결되는지**를 정리
- 근거: 수집한 논문 초록과 제품 문서·README 원문 ([논문 목록](../reference/papers/README.md), [사례 목록](../reference/cases/README.md))
- 한계: 논문은 초록만 확인했다. 초록에 없는 내부 구조는 쓰지 않았고, 추정이면 "(추정)"으로 표시했다.
- 비교 보고서: [에이전트 메모리 설계 비교](../report/2026_10_27_agent-memory-design-comparison.md)

## 한눈에 보기

| # | 카테고리 | 핵심 아이디어 | 대표 방법론 | 주로 쓰이는 곳 |
|---|---|---|---|---|
| 1 | 파일 기반 계층 메모리 | 마크다운 파일에 쓰고, 작은 색인만 상시 로딩, 나머지는 필요할 때 읽기 | Claude Code auto memory, Claude memory tool, Letta MemFS, Manus | 코딩·장기 작업 에이전트 |
| 2 | OS형 계층 메모리 | 컨텍스트를 RAM, 외부 저장소를 디스크처럼 나눠 페이징 | MemGPT/Letta, MemoryOS, MemOS, MIRIX, LightMem | 장기 대화·개인화 에이전트 |
| 3 | 추출·통합 메모리 레이어 | 대화에서 사실을 LLM으로 추출 → 통합 → 하이브리드 검색으로 주입 | Mem0, CrewAI Memory, LangMem, GitHub Copilot Memory | 챗봇·SaaS에 붙이는 메모리 API |
| 4 | 시간 인지 지식그래프 | 엔티티·관계로 저장, 사실에 유효기간을 두고 그래프 탐색으로 검색 | Zep/Graphiti, HippoRAG 1·2, A-MEM, G-Memory | 엔터프라이즈 데이터·관계 추론 |
| 5 | 경험·절차 메모리 (self-evolving) | 성공·실패 궤적에서 전략·워크플로우를 증류해 다음 작업에 재사용 | AWM, ReasoningBank, ACE, Dynamic Cheatsheet, Memp, MemRL | 웹·코딩·도구 사용 에이전트 |
| 6 | RL로 학습된 메모리 관리 | 무엇을 저장·갱신·삭제할지를 강화학습으로 학습 | Memory-R1, Mem-α, MEM1, MemAgent, Memory-T1 | 연구 단계 |

- 1·3은 실서비스에서 가장 많이 쓰이고, 5·6은 2025년 이후 논문에서 가장 빠르게 늘어난 방향이다. [Second Half 서베이](../reference/papers/survey_agent_memory_second_half_arxiv-2602.06052.md)는 2025년에만 "hundreds of papers"가 나왔다고 하고, 메모리 관리 자체가 "trainable capability"가 되는 흐름을 짚는다.
- 대부분의 실서비스는 하나만 쓰지 않는다. 예: Letta = 1 + 2, Mem0 = 3 + 4(그래프 변형).

## 1. 파일 기반 계층 메모리

> "Rather than loading all relevant information up front, an agent records what it learns in memory files and reads them back on demand." — [Claude memory tool docs](../reference/cases/claude-memory-tool_anthropic-docs.md)

### 공통 구조

```
            ┌──────────── 컨텍스트 윈도우 ────────────┐
            │ system prompt                           │
            │ + 색인 파일 (항상 로딩, 크기 제한)  ◄───┼── MEMORY.md / system/
            │ + 대화                                  │
            └───────────┬──────────────▲──────────────┘
         파일 도구로 쓰기 │              │ 필요할 때 읽기 (view / read / grep)
                        ▼              │
            ┌──────────── 파일시스템 (마크다운) ───────┐
            │ topic_a.md   topic_b.md   skills/ ...   │  ← git 버전관리(Letta)
            └─────────────────────────────────────────┘
```

- 저장: 사람이 읽고 고칠 수 있는 마크다운. 벡터 인덱스를 쓰지 않는 경우가 많다 ("MemFS does not include a semantic or vector index by default", [Letta MemFS](../reference/cases/letta-memfs_letta-docs.md)).
- 쓰기: 에이전트가 루프 안에서 파일 도구로 직접 쓴다.
- 읽기: 색인(목록)만 항상 넣고, 본문은 에이전트가 필요할 때 연다 (just-in-time).

### 대표 방법론

**Claude Code auto memory** ([docs](../reference/cases/claude-code-memory_anthropic-docs.md))
- 구성: `MEMORY.md` 색인 + 메모리 하나당 주제 파일 하나 (YAML frontmatter, 타입 `user` / `feedback` / `project` / `reference`)
- 로딩: `MEMORY.md`는 시작 시 "first 200 lines or 25KB"까지, 주제 파일은 필요할 때
- 지시와 분리: 사람이 쓰는 `CLAUDE.md`(규칙)와 Claude가 쓰는 auto memory(학습)를 따로 둔다. 코드에서 알 수 있는 것은 저장하지 않는다.
- 범위: git 저장소 단위

**Claude memory tool** ([docs](../reference/cases/claude-memory-tool_anthropic-docs.md), [발표](../reference/cases/claude-context-management_anthropic-news.md))
- 구성: 가상 `/memories` 디렉터리 + 명령 6개 (view, create, str_replace, insert, delete, rename)
- 실행 위치: "operates entirely client-side through tool calls" — 저장소 백엔드는 개발자가 구현
- 짝: context editing(오래된 도구 결과 자동 삭제)과 함께 쓸 때 Anthropic 내부 평가 39% 개선
- 프롬프트 규약: "ASSUME INTERRUPTION" — 컨텍스트가 언제든 리셋될 수 있으니 진행 상황을 파일에 남기라고 지시

**Letta MemFS** ([memory](../reference/cases/letta-memory_letta-docs.md), [MemFS](../reference/cases/letta-memfs_letta-docs.md))
- 구성: 에이전트 소유 git 저장소. `system/` 아래 파일은 매 턴 system prompt에 포함, 나머지는 파일 트리만 보이고 필요할 때 읽음
- 쓰기: 에이전트가 직접 편집 + 백그라운드 "dreaming" 서브에이전트가 최근 대화를 검토·통합 (트리거: `step-count` / `compaction-event`)
- 동시성: 서브에이전트가 git worktree로 병렬 편집, 모든 편집이 커밋 → 버전 이력·충돌 해결

**Manus** ([blog](../reference/cases/manus-context-engineering_manus-blog.md))
- 작업 중 메모리(working memory)에 해당. 파일시스템을 "the ultimate context"로 사용
- 큰 관찰 결과는 파일로 빼고 경로·URL만 컨텍스트에 남김 → 복원 가능한 압축
- `todo.md`를 계속 다시 써서 목표를 컨텍스트 끝에 유지 ("recitation")
- 실패 기록을 지우지 않고 남김 ("leave the wrong turns in the context")

### 장단점
- 장점: 사람이 보고 고칠 수 있음, git 이력, 모델이 이미 잘 쓰는 파일 도구를 재사용
- 단점: 충돌 해결이 약함 (Claude Code: "Claude may pick one arbitrarily"), 항목이 많아질 때의 검색 성능 근거 없음

## 2. OS형 계층 메모리

> "virtual context management, a technique drawing inspiration from hierarchical memory systems in traditional operating systems" — [MemGPT](../reference/papers/memgpt_arxiv-2310.08560.md)

### 공통 구조

```
  ┌───────── 주 컨텍스트 (RAM) ─────────┐
  │ core memory blocks (persona, human) │◄── 항상 in-context
  │ 최근 메시지 (FIFO)                  │
  └──────┬──────────────────▲───────────┘
   밀려남 │                  │ 검색 도구 호출
         ▼                  │
  ┌─────────── 외부 저장소 (디스크) ───────────┐
  │ recall memory   : 전체 대화 이력          │
  │ archival memory : 명시적으로 저장한 기억  │
  └────────────────────────────────────────────┘
```

### 대표 방법론

**MemGPT → Letta** ([논문](../reference/papers/memgpt_arxiv-2310.08560.md), [sleep-time blog](../reference/cases/letta-sleep-time-compute_letta-blog.md))
- 계층 3개: core memory (in-context memory blocks) / recall memory (대화 이력) / archival memory (저장한 기억)
- 제어: LLM이 메모리 계층을 스스로 관리하고, interrupt로 사용자와의 제어 흐름 관리 (계층 간 이동 방식 세부는 본문 미확인)
- Sleep-time 확장 (2025-04): 에이전트를 두 개 띄운다
  - primary agent: 사용자 응답, 외부 메모리 검색만 가능. core memory 편집 도구 없음
  - sleep-time agent: core memory 편집 도구를 가지고 비동기로 메모리를 정리. "raw context"를 "learned context"로 변환
  - 이유: "Memory formation in MemGPT is incremental, so memories may become messy and disorganized over time"

**MemoryOS** ([논문](../reference/papers/memoryos_arxiv-2506.06326.md))
- 모듈 4개: Storage, Updating, Retrieval, Generation
- 저장 3단: short-term → mid-term → long-term personal memory
- 이동 규칙: 단기→중기는 대화 체인 기반 FIFO, 중기→장기는 segmented page 구성

**MemOS** ([논문](../reference/papers/memos_arxiv-2507.03724.md), [README](../reference/cases/memos_github-readme.md))
- 메모리를 시스템 자원으로 관리: plaintext / activation / parameter 메모리를 하나의 스케줄러로 통합
- 기본 단위 MemCube: 내용 + provenance·versioning 메타데이터. 합성·이동·융합 가능
- 실구현: 그래프 + 벡터 (Neo4j + Qdrant, 로컬은 SQLite FTS5 + vector), MemScheduler로 비동기 쓰기

**MIRIX** ([논문](../reference/papers/mirix_arxiv-2507.07957.md))
- 메모리 6종: Core, Episodic, Semantic, Procedural, Resource Memory, Knowledge Vault
- 멀티에이전트 프레임워크가 갱신·검색을 동적으로 조율 (종류별 에이전트 배치 여부는 본문 미확인)
- 멀티모달(화면 스크린샷) 입력 지원

**LightMem** ([논문](../reference/papers/lightmem_arxiv-2510.18866.md))
- Atkinson-Shiffrin 3단계: sensory(경량 압축으로 불필요 정보 필터, 주제별 그룹) → topic-aware short-term(그룹 통합·요약) → long-term
- 장기 메모리 갱신을 온라인 추론에서 떼어 오프라인 "sleep-time update"로 처리 → 토큰 최대 38배 절감 (LongMemEval)

### 장단점
- 장점: 컨텍스트 크기를 넘는 장기 기억을 체계적으로 관리, 계층별 정책 분리
- 단점: 계층·모듈이 많아 구현 복잡, 계층 간 이동 규칙이 휴리스틱

## 3. 추출·통합 메모리 레이어

> "dynamically extracting, consolidating, and retrieving salient information from ongoing conversations" — [Mem0](../reference/papers/mem0_arxiv-2504.19413.md)

애플리케이션 옆에 붙이는 "메모리 API" 형태. 대화가 끝날 때마다 사실을 뽑아 저장하고, 다음 요청 전에 관련 기억을 검색해 넣는다.

### 공통 구조

```
 대화 턴 ──► [추출 LLM] ──► 후보 사실들 ──► [통합] ──► 저장소 (벡터 + 키워드 + 엔티티)
                                         │                         │
                         ADD / UPDATE /  │                         │
                         DELETE / NOOP   │                         │
                         또는 ADD-only    │                         ▼
 새 요청 ─────────────────────────────────────────────► [하이브리드 검색 + 재순위]
                                                                   │
                                                     system prompt에 주입 ◄┘
```

### 대표 방법론

**Mem0** ([논문](../reference/papers/mem0_arxiv-2504.19413.md), [README](../reference/cases/mem0_github-readme.md))
- 2025-04 논문: 추출·통합·검색 파이프라인 + 그래프 기반 변형 (기본 대비 약 2% 향상)
- 현재 README의 새 알고리즘:
  - 추출: "Single-pass ADD-only extraction -- one LLM call, no UPDATE/DELETE." 덮어쓰지 않고 누적
  - 엔티티 링크: 엔티티를 추출·임베딩해 기억 간 연결
  - 검색: "semantic, BM25 keyword, and entity matching scored in parallel and fused"
  - 최신성: 갱신 대신 검색 시 시간 인지 랭킹으로 처리
- 의미: 논문 시기의 "LLM이 갱신 판단"에서 "누적 + 검색 시 판단"으로 이동

**CrewAI Memory** ([docs](../reference/cases/crewai-memory_crewai-docs.md))
- 쓰기: 태스크 후 사실 추출, LLM이 scope·category·importance 추론
- 통합: 유사도 0.85 초과 시 LLM이 keep / update / delete / insert_new 결정, 배치 내 0.98 이상은 중복 제거
- 읽기: 태스크 전 회상. 점수 = semantic 0.5 + recency 0.3 + importance 0.2 (recency 반감기 30일)
- 범위: 계층형 scope 트리, 에이전트별 private scope

**LangMem / LangGraph** ([LangMem](../reference/cases/langmem_github-readme.md), [LangGraph](../reference/cases/langgraph-memory_langchain-docs.md))
- 쓰기 경로 2개: hot path(에이전트가 `manage_memory` 도구 호출) / background(별도 매니저가 추출·통합)
- 저장: namespace + key 단위 JSON 문서. semantic 메모리는 profile(문서 하나 갱신) 또는 collection(문서 여러 개)
- 설계 조언: "It's easier for an LLM to generate new objects for new information than reconcile new information with an existing profile."

**GitHub Copilot Memory** ([blog](../reference/cases/copilot-agentic-memory_github-blog.md), [docs](../reference/cases/copilot-memory_github-docs.md))
- 저장 단위: `subject`, `fact`, `citations`(file:line), `reason`을 가진 JSON
- 쓰기: 에이전트가 `store_memory` 도구를 루프 안에서 호출
- 읽기: 저장소의 최근 메모리를 주입 → 인용된 코드 위치를 현재 브랜치에서 확인 → "Only validated facts are used"
- 정리: 오프라인 큐레이션을 비용 때문에 생략하고 읽을 때 검증으로 대체. 코드와 어긋나면 수정본을 다시 저장, 28일간 안 쓰면 자동 삭제
- 3번 카테고리 중 "검증" 단계를 넣은 변형

### 장단점
- 장점: 어떤 앱에도 붙이기 쉬움, 검색 비용 낮음 (Mem0 논문: full-context 대비 p95 지연 91%↓)
- 단점: 갱신 판단이 어려움 (LangGraph: "over-inserting" / "over-updating"), 벤치마크 수치가 벤더마다 자체 측정

## 4. 시간 인지 지식그래프

> "Facts have validity windows. When information changes, old facts are invalidated — not deleted." — [Graphiti README](../reference/cases/graphiti_github-readme.md)

### 공통 구조

```
 원본 데이터 (대화·문서·JSON)
        │
        ▼
   [Episode 저장] ── 원본 그대로, 모든 사실의 출처
        │
        ▼ LLM 추출 + 중복 제거 + 모순 판단
   ┌──────────────── Graph ────────────────┐
   │ Entity ──(Fact, valid_from~valid_to)──► Entity │
   │   └ 요약이 계속 갱신됨                         │
   │ Community (엔티티 군집 요약)                   │
   └──────────────────────────────────────────────┘
        │
        ▼ 검색 = 임베딩 + BM25 + 그래프 탐색 (+ 그래프 거리 재순위)
```

### 대표 방법론

**Zep / Graphiti** ([논문](../reference/papers/zep_arxiv-2501.13956.md), [README](../reference/cases/graphiti_github-readme.md))
- 구성요소: Entities(요약이 진화) / Facts·Edges(유효기간이 있는 triplet) / Episodes(원본, provenance) / Communities
- 시간: bi-temporal 추적. 새 정보가 기존 사실과 모순되면 옛 사실을 무효화하고 이력은 유지
- 검색: "Combines semantic embeddings, keyword (BM25), and graph traversal… without reliance on LLM summarization"
- 저장소: Neo4j, FalkorDB, Neptune
- Zep 논문 보고: DMR 94.8% (MemGPT 93.4%), LongMemEval 최대 18.5% 향상, 지연 90%↓

**HippoRAG / HippoRAG 2** ([1](../reference/papers/hipporag_arxiv-2405.14831.md), [2](../reference/papers/hipporag2_arxiv-2502.14802.md))
- 해마 색인 이론 비유: LLM(신피질) + 지식그래프(해마 색인) + Personalized PageRank(연상 검색)
- HippoRAG 1: 단일 단계 검색으로 반복 검색(IRCoT)과 비슷하거나 더 좋은 성능, "10-30 times cheaper and 6-13 times faster"
- HippoRAG 2: 그래프 기반 RAG가 단순 사실 검색에서 일반 RAG보다 떨어지는 문제를 passage 통합 강화로 해결

**A-MEM** ([논문](../reference/papers/a_mem_arxiv-2502.12110.md))
- Zettelkasten 방식: 새 기억마다 구조화된 노트(맥락 설명, 키워드, 태그) 생성
- 링크: 기존 기억과 의미적으로 비슷하면 링크 생성
- 진화: 새 기억이 들어오면 기존 기억의 설명·속성도 갱신 ("memory evolution")
- 엄밀한 KG라기보다 노트 네트워크 (그래프 DB 비의존)

**G-Memory** ([논문](../reference/papers/g_memory_arxiv-2506.07398.md))
- 멀티에이전트용 3층 그래프: insight graph / query graph / interaction graph
- 검색: 위로는 일반화된 insight, 아래로는 압축된 협업 궤적을 양방향 탐색

### 장단점
- 장점: 관계·시간 추론("지금은 어디 살지?"), 출처 추적, 사실 변경 이력 보존
- 단점: 수집 시 LLM 호출이 많음 (Graphiti는 동시성 한도 `SEMAPHORE_LIMIT` 기본 10), 그래프 DB 운영 필요

## 5. 경험·절차 메모리 (self-evolving)

> "contexts as evolving playbooks that accumulate, refine, and organize strategies" — [ACE](../reference/papers/ace_arxiv-2510.04618.md)

"사용자에 대한 사실"이 아니라 "일을 잘하는 방법"을 기억한다. 가중치를 바꾸지 않고 메모리만으로 성능이 오르는 test-time learning.

### 공통 구조

```
 작업 수행 ──► 궤적 (행동 + 결과)
                  │
                  ▼
           [평가] 성공/실패 — 자기 판단 또는 환경 피드백
                  │
                  ▼
           [증류] 재사용 가능한 전략·워크플로우·코드 조각으로 추상화
                  │
                  ▼
           메모리 (playbook / workflow / cheatsheet / skill library)
                  │
 다음 작업 ◄──── [관련 항목 검색해 프롬프트에 주입]
```

### 대표 방법론

**Agent Workflow Memory (AWM)** ([논문](../reference/papers/agent_workflow_memory_arxiv-2409.07429.md))
- 과거 작업에서 자주 재사용되는 루틴(workflow)을 유도해 선택적으로 제공
- 오프라인(학습 예시에서 미리) / 온라인(테스트 쿼리에서 즉석) 둘 다 가능
- Mind2Web 24.6%, WebArena 51.1% 상대 성공률 향상

**ReasoningBank** ([논문](../reference/papers/reasoningbank_arxiv-2509.25140.md))
- 스스로 판정한 **성공과 실패** 경험 모두에서 일반화 가능한 추론 전략을 증류
- 루프: 검색 → 작업에 활용 → 새 학습을 다시 통합
- MaTTS(memory-aware test-time scaling): 작업당 더 많은 시도를 돌려 대조 신호를 얻고, 더 좋은 메모리를 합성
- 원본 궤적만 저장하거나 성공 루틴만 저장하는 방식보다 낫다고 보고

**ACE (Agentic Context Engineering)** ([논문](../reference/papers/ace_arxiv-2510.04618.md))
- 역할 3개: Generation → Reflection → Curation (모듈형 프로세스)
- 핵심: 전체를 다시 쓰지 않고 "structured, incremental updates"로 갱신해 두 가지 실패를 막음
  - brevity bias: 요약하다 도메인 세부를 버림
  - context collapse: 반복 재작성으로 세부가 깎임
- 오프라인(system prompt)과 온라인(agent memory) 둘 다 최적화, 라벨 없이 실행 피드백만으로 적응
- 에이전트 +10.6%, 금융 +8.6%

**Dynamic Cheatsheet** ([논문](../reference/papers/dynamic_cheatsheet_arxiv-2504.07952.md))
- 블랙박스 LM에 지속·진화하는 cheatsheet를 붙임: 전략, 코드 조각, 문제 풀이 통찰
- 전체 대화가 아니라 "concise, transferable snippets"만 스스로 큐레이션
- GPT-4o Game of 24: 10% → 99% (찾아낸 Python 풀이를 재사용)

**Memp** ([논문](../reference/papers/memp_arxiv-2508.06433.md))
- 궤적을 두 수준으로 증류: 세부 단계별 지시 + 상위 스크립트형 추상화
- Build / Retrieval / Update 전략을 따로 실험, 계속 갱신·수정·폐기
- 강한 모델이 만든 절차 메모리를 약한 모델로 옮겨도 효과 유지

**MemRL** ([논문](../reference/papers/memrl_arxiv-2601.03192.md))
- 추론(안정)과 메모리(가소성)를 분리, 에피소드 메모리 위에서 RL로 진화 (가중치 불변)
- Two-Phase Retrieval: 의미 유사도로 후보를 뽑은 뒤 환경 피드백으로 "high-utility" 전략을 골라 노이즈 제거

**원형(2023)**: [Voyager](../reference/papers/voyager_arxiv-2305.16291.md) — 실행 가능한 코드 스킬 라이브러리 / [ExpeL](../reference/papers/expel_arxiv-2308.10144.md) — 학습 과제에서 자연어 통찰 추출 / [Reflexion](../reference/papers/reflexion_arxiv-2303.11366.md) — 실패에 대한 자기 반성 텍스트를 에피소드 버퍼에 저장

**실서비스 대응물**: CLAUDE.md, Cursor rules, AGENTS.md, Letta skills. 구조는 같지만(재사용 가능한 절차를 텍스트로) 대부분 사람이 쓰거나 검토한다. Cursor 권고: "Add rules only when you notice Agent making the same mistake repeatedly" ([docs](../reference/cases/cursor-rules_cursor-docs.md)).

### 장단점
- 장점: 가중치 학습 없이 성능 향상, 메모리를 다른 모델로 이식 가능 (Memp)
- 단점: 잘못된 전략도 누적될 수 있음, 평가 신호(성공 판정)의 품질에 좌우됨

## 6. RL로 학습된 메모리 관리

> "most existing pipelines are static and heuristic-driven, lacking a learned mechanism for deciding what to store, update, or retrieve" — [Memory-R1](../reference/papers/memory_r1_arxiv-2508.19828.md)

1·3번 카테고리에서 프롬프트 규칙이나 임계값으로 정하던 "무엇을 저장·갱신·삭제할까"를 모델이 보상으로 학습한다. 보상은 대부분 하류 QA 정답률.

### 구조 유형 두 가지

```
 (a) 외부 메모리 + 학습된 매니저               (b) 내부 상태를 매 턴 다시 쓰기
                                               
 입력 ─► [Memory Manager] ─► ADD/UPDATE/      입력 chunk_t + state_{t-1}
                DELETE/NOOP ─► 메모리 뱅크              │
 질문 ─► [Answer Agent] ◄─ 후보 선별 ─┘                ▼
                │                               [LLM] ─► state_t (고정 크기, overwrite)
          정답 여부 = 보상 (PPO/GRPO)                  │
                                                최종 답 정답 여부 = 보상
 Memory-R1, Mem-α, Memory-T1                   MEM1, MemAgent
```

### 대표 방법론

**Memory-R1** ([논문](../reference/papers/memory_r1_arxiv-2508.19828.md)) — 유형 (a)
- 에이전트 2개: Memory Manager(ADD / UPDATE / DELETE / NOOP 학습) + Answer Agent(관련 항목을 미리 골라 추론)
- 학습: 결과 기반 RL (PPO, GRPO), 학습 QA 쌍 152개
- LoCoMo, MSC, LongMemEval, 3B~14B 모델에서 일반화

**Mem-α** ([논문](../reference/papers/mem_alpha_arxiv-2509.25911.md)) — 유형 (a)
- 메모리 구조: core / episodic / semantic 3요소 + 메모리 조작 도구들
- 학습: 정보를 청크 단위로 순차 처리하며 추출·저장·갱신, 보상은 전체 이력에 대한 QA 정답률
- 30k 토큰으로 학습해 400k 토큰 이상(13배)으로 일반화

**Memory-T1** ([논문](../reference/papers/memory_t1_arxiv-2512.20092.md)) — 유형 (a), 읽기 쪽
- coarse-to-fine: 시간·관련성 필터로 후보 세션 축소 → RL 에이전트가 근거 세션 선택
- 보상 3종: 정답 정확도, 근거 일치, 시간 일관성

**MEM1** ([논문](../reference/papers/mem1_arxiv-2506.15841.md)) — 유형 (b)
- 매 턴 "compact shared internal state"를 갱신: 기억 통합과 추론을 한 상태에서 처리, 불필요한 정보는 버림
- 메모리 사용량이 턴 수와 무관하게 일정
- Qwen2.5-14B 대비 성능 3.5배, 메모리 3.7배 절감 (16목표 multi-hop QA)

**MemAgent** ([논문](../reference/papers/memagent_arxiv-2507.02259.md)) — 유형 (b)
- 긴 문서를 구간별로 읽으며 메모리를 덮어쓰기(overwrite)로 갱신
- DAPO를 확장해 학습, 32K 텍스트로 학습한 8K 컨텍스트 모델이 3.5M QA로 외삽 (성능 손실 < 5%)

### 장단점
- 장점: 휴리스틱 대신 데이터로 저장 정책을 최적화, 적은 데이터로도 효과 (Memory-R1 152쌍)
- 단점: 모델 학습이 필요해 API 모델에 바로 적용 불가, 수집 자료 중 실서비스 적용 사례 없음
