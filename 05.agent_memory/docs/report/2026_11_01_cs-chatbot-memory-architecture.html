CS 챗봇 메모리 구조: 규정 문서 + 과거 대응 기록

  • 작성일: 2026-11-01
  • 선행 보고서: 에이전트 메모리 설계 비교, 노트: 아키텍처 패턴 6개 카테고리
  • 범위 주의: 이 보고서는 실험 결과가 아니라 수집한 자료를 CS 상황에 맞춰 조합한 설계 제안이다. 수집 자료 중 CS 챗봇을 직접 다룬 벤치마크는 없고, 논문은 초록만 읽었다.

1. 목적

CS 챗봇이 답할 때 주로 하는 일은 규정 문서와 과거 대응 기록을 불러오는 것이다. 이 상황에서 어떤 메모리 구조가 가장 적합한지, 그리고 왜 다른 구조는 맞지 않는지 정리한다.

2. 방법

  • 선행 보고서·노트의 6개 카테고리(파일 기반 / OS식 계층 / 추출·통합 / 시간 지식 그래프 / 경험 메모리 / 강화학습 관리)를 CS 요구사항에 대입했다.
  • 추천 구조의 각 구성요소마다 근거가 된 원문(docs/reference/)을 다시 열어 해당 문장을 확인했다.
  • 확인 과정에서 앞선 답변의 오류 1건을 고쳤다: "기존 기억과 비교해 keep/update/delete를 LLM이 결정"하는 통합 방식의 근거로 Mem0를 들었으나, 현재 Mem0 README는 "ADD-only extraction -- one LLM call, no UPDATE/DELETE"이고 논문 초록에는 해당 연산이 명시되지 않는다. 이 방식의 근거는 CrewAI Memory로 바꿨다.

3.3 구성요소별 설계와 근거

① 규정 저장소: 정답 원본

  • 규정은 요약하지 않고 조항 단위로 그대로 둔다. 메타데이터: 조항 ID / 버전 / 시행일. 검색은 현재 유효 버전만.
  • 규정 양이 적으면 벡터 검색 대신 "작은 색인은 항상 주입, 본문은 필요할 때 연다"를 쓸 수 있다. 조각으로 잘리지 않아 조항 문구가 그대로 들어간다.
    "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." — Claude Code docs
  • 규정이 많으면 조항 단위 하이브리드 검색(키워드 + 의미)으로 바꾼다. 색인 방식이 버티는 규모는 확인하지 않았다.

② 사례 메모리: 원본 로그 대신 카드

  • 상담 대화를 통째로 넣지 않고, 종결 건만 LLM으로 상황 → 판단 → 근거 조항(버전) → 결과 카드로 추출한다.
  • 새 카드가 기존 카드와 비슷하면 LLM이 유지·수정·삭제·새로 추가 중에서 결정한다.
    "If the similarity is above consolidation_threshold (default 0.85), the LLM decides what to do" (keep / update / delete / insert_new) — CrewAI Memory docs
  • 실패·에스컬레이션 건도 "이럴 땐 이렇게 하면 안 된다"는 교훈 카드로 남긴다.
    ReasoningBank는 "self-judged successful and failed experiences"에서 전략을 추출한다 — ReasoningBank (초록)

③ 규정–사례 연결: 가장 중요한 부분

  • 가장 큰 위험은 규정이 바뀌었는데 옛 사례를 근거로 답하는 것이다.
  • 카드에 근거 조항과 버전을 달고, 사용하기 전에 현재 버전과 대조한다. 다르면 사용하지 않고 재검토로 넘긴다.
    "we store memories with citations: references to specific code locations that support each fact. When an agent encounters a stored memory, it verifies the citations in real-time" — GitHub Copilot 블로그
  • 규정 개정 시 해당 조항을 인용한 카드를 한꺼번에 무효화한다. Graphiti의 사실별 유효 기간을 그래프 없이 버전 태그로 단순화한 것이다.
    "Facts have validity windows. When information changes, old facts are invalidated" — Graphiti README

④ 답변 규칙

  • 규정 최우선. 사례는 "이 규정이 실제로 이렇게 적용됐다"는 예시로만 쓴다.
  • 규정과 사례가 충돌하면 규정을 따르고, 그 카드는 재검토로 표시한다.
  • 답변에 근거 조항을 인용한다.

3.4 제외한 구조

구조제외 이유
OS식 계층 (MemGPT 등)긴 대화의 컨텍스트 관리가 핵심 기능인데, CS 대화는 짧아 이점이 작다
강화학습 메모리 관리 (Memory-R1 등)학습 데이터·비용이 들고, 왜 그 기억을 쓰고 지웠는지 감사하기 어렵다
완전한 시간 지식 그래프 (Zep/Graphiti)필요한 건 "조항 버전" 하나의 유효성뿐이라 버전 태그로 충분하다. 고객·주문·상품 관계를 따라가는 질문이 많으면 다시 고려하되, 그 정보는 보통 CRM·주문 DB 도구 조회가 낫다

4. 해석

  • CS 챗봇에서 "메모리"라고 부를 대상은 사실상 사례 메모리 하나다. 규정은 바뀌지 않는 한 그대로 꺼내야 하는 원본이라, 메모리 시스템의 추출·요약을 거치면 오히려 위험하다.
  • 그래서 일반 대화형 메모리 구조를 그대로 가져오기보다, 원본(규정)과 경험(사례)을 분리하고 그 사이에 버전 검증을 두는 것이 이 상황의 핵심 설계다.
  • 사용 전 검증은 Copilot이 오프라인 정리 비용을 피하려고 고른 방식이다. CS에서도 규정 개정이 드물다면 주기적 일괄 정리보다 싸다.

5. 남은 질문

  • 규정 양이 어느 정도까지 "색인 + 필요 시 열기"로 버티는지 (미측정)
  • 사례 카드 추출 품질: 틀린 과거 답변을 걸러낼 기준 (정상 종결, 만족도 등) — 운영 데이터로 확인 필요
  • 개인정보 제거를 추출 단계에서 얼마나 확실히 할 수 있는지
  • 사례 카드를 넣었을 때 규정만 쓸 때보다 정답률이 실제로 오르는지 — 실험으로 비교 필요
