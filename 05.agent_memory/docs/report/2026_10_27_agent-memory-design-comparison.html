1. 목적

에이전트 메모리를 만들 때 실제로 내려야 하는 설계 결정이 무엇이고, 연구와 실서비스가 각 결정에서 어떤 선택을 하는지 비교한다.

2. 방법

  • 자료: 2023-03 ~ 2026-05 arXiv 논문 48편 (아키텍처 28, 학습/메모리 관리 9, 서베이 6, 벤치마크 5), 제품 문서·블로그·README 34건 (상용 어시스턴트 8, 코딩 에이전트 7, 오픈소스 14, 엔지니어링 글 5). 모두 2026-10-27 수집.
  • 비교 축: 서베이들이 공통으로 쓰는 축을 합쳐 6개로 정했다.
  • Rethinking Memory의 6개 연산 (Consolidation, Updating, Indexing, Forgetting, Retrieval, Condensation)
  • Memory in the Age of AI Agents의 형태(token-level / parametric / latent)와 기능(factual / experiential / working)
  • CoALA의 semantic / episodic / procedural 구분
  • 결정 축 6개: ① 무엇을 저장하나 ② 어떤 형태로 저장하나 ③ 누가·언제 쓰나 ④ 어떻게 컨텍스트로 불러오나 ⑤ 갱신·충돌·망각 ⑥ 범위·사용자 통제
  • 사례 원문은 별도 패스로 시스템별 사실(저장 대상·쓰기/읽기 경로·수치)을 인용과 함께 추출하고, 핵심 인용 9개는 원문 파일에서 grep으로 재확인했다.

LLM이 CRUD 결정 Mem0 논문 (초록 표현은 "extracting, consolidating" — 세부 연산은 본문 미확인), CrewAI (유사도 0.85 초과 시 keep/update/delete/insert_new), Memory-R1 (이 결정을 RL로 학습) LangGraph: "some models may default to over-inserting and others may default to over-updating"

사용 시점 검증 + 미사용 만료 GitHub Copilot 미사용 항목 "automatically deleted after 28 days", 검증·사용 시 타이머 리셋 가능
망각 곡선 MemoryBank Ebbinghaus 곡선 기반 경과시간·중요도로 망각/강화
오프라인 통합 Letta dreaming, LightMem (sleep-time update), Generative Agents (reflection) —

정리 없음 / 사람·개발자 몫 Claude Code (충돌 시 "Claude may pick one arbitrarily"), Claude memory tool ("Periodically delete memory files that haven't been accessed in a long time" 권고) —
  • 반복 갱신의 함정: ACE는 반복 재작성이 세부를 깎아내는 "context collapse"와 요약 편향 "brevity bias"를 지적하고, 전체 재작성 대신 구조화된 증분 갱신을 쓴다. Manus도 "any irreversible compression carries risk"라며 복원 가능한 압축(URL·경로 보존)만 쓴다.
  • GitHub는 오프라인 큐레이션(중복 제거·충돌 해결)을 비용 때문에 명시적으로 기각하고 읽을 때 검증으로 대체했다: "Information retrieval is an asymmetrical problem: It's hard to solve, but easy to verify" (출처).

3.6 범위·사용자 통제

  • 범위를 좁히는 것이 기본: 프로젝트별 (Claude 앱 "a separate memory for each project", 출처), 저장소별 (Claude Code, Copilot), 워크스페이스별 (Windsurf "Memories generated in one workspace will not be available in another", 출처). Anthropic은 프로젝트 분리를 "a safety guardrail"로 설명.
  • 권한과 연동: Copilot 저장소 메모리는 쓰기 권한자 활동에서만 생성, 읽기 권한자는 사용만 (출처).
  • 상용 어시스턴트 공통 통제: 보기·수정·삭제, 전체 끄기, 메모리 없는 모드 (ChatGPT Temporary chat, Claude Incognito, Gemini Temporary Chat — 최대 72시간 보관, 출처), 저장 알림 ("Memory updated").
  • 기본값은 갈린다: Gemini 과거 대화 참조 "on by default", Claude 앱 "fully optional", Copilot은 개인 요금제 기본 켜짐·엔터프라이즈는 관리자 활성화 필요.
  • 삭제는 연쇄되지 않는다: "Deleting a chat doesn't erase its memories; you must delete the memory itself" (ChatGPT blog). 삭제된 저장 메모리 로그는 최대 30일 보관 가능 (FAQ).
  • 다중 사용자·다중 에이전트 공유: CrewAI private scope·slice, MemOS cube, G-Memory. Graphiti 참조 서버는 "no authentication, no authorization, and no prompt-injection protection"이라고 스스로 밝힘 (출처).

4. 해석

  1. 연구와 실서비스가 다른 문제를 풀고 있다.
  2. 논문은 저장 구조(그래프·계층·latent)와 학습된 관리 정책(RL)에 집중한다.
  3. 실서비스, 특히 코딩 에이전트는 마크다운 파일 + 작은 색인 상시 로딩 + 나머지 필요시 읽기로 수렴했다 (Claude Code, Letta MemFS, Codex, Cursor, Windsurf, Manus).
  4. 이유로 문서들이 드는 것: 사람이 읽고 고칠 수 있음, git으로 버전 관리, 모델이 이미 파일 도구를 잘 씀.
  5. 실서비스의 핵심 난제는 "찾기"보다 "아직 맞는가"다.
  6. GitHub: "The core challenge for memory systems isn't about information retrieval, but ensuring that any stored knowledge remains valid as code evolves" (출처).
  7. 대응이 셋으로 갈린다: 읽을 때 검증(Copilot), 지우지 않고 유효기간 표시(Graphiti), 백그라운드 재정리(Letta). 무엇이 나은지 비교한 자료는 수집 범위에 없다.
  8. 갱신 연산은 아직 합의가 없다.
  9. Mem0는 논문(2025-04)에서 LLM이 추출·통합하던 방식에서 현 README의 ADD-only로 바뀌었다. 위 LangGraph 지적("over-inserting / over-updating")과 ACE의 context collapse가 같은 문제의 다른 면으로 보인다 (추정).
  10. RL 논문들(Memory-R1, Mem-α)은 바로 이 결정을 학습 대상으로 삼는다.
  11. 메모리의 중심이 "사용자 사실"에서 "경험·절차"로 옮겨 가는 중.
  12. 2024-09 AWM 이후 Memp, ReasoningBank, ACE, Dynamic Cheatsheet, MemRL 모두 가중치를 바꾸지 않고 전략·워크플로우를 쌓아 성능을 올린다.
  13. 실서비스에서 같은 위치를 차지하는 것이 CLAUDE.md·rules·skills다. 차이는 실서비스는 대부분 사람이 쓰거나 사람이 검토한다는 점.
  14. 벤치마크 수치는 설계 판단 근거로 약하다.
  15. LoCoMo·LongMemEval 점수가 벤더마다 자체 측정이고 서로 다른 설정이다.
  16. 실제 효과 근거로는 GitHub의 A/B 테스트가 가장 구체적이지만 효과 크기는 작다 (머지율 +7%p).

5. 남은 질문

  • 논문 본문 미확인: 위 아키텍처 비교는 초록 수준. Mem0·Zep·A-MEM·MemGPT·LongMemEval은 본문(특히 실험 설정)을 읽어야 수치 비교가 가능.
  • ChatGPT·Gemini·Claude 앱의 저장·검색 내부 구조는 공개 문서에 없음. ChatGPT가 save_memories 도구로 upsert한다는 것은 LangGraph 문서의 2차 언급뿐 (출처).
  • 갱신 전략(append-only / LLM CRUD / 무효화 / 읽기 시 검증)을 같은 조건에서 비교한 자료 없음 → 직접 실험 후보.
  • 파일 기반 메모리가 수천 항목 이상으로 커질 때의 한계 (색인 200줄 제한 이후) 관련 자료 없음.
  • 2026-06 이후 쏟아진 메모리 벤치마크(약 25편)는 영향력 판단이 어려워 수집에서 제외. 필요하면 추가 조사.
  • 메모리 오염·프롬프트 인젝션 같은 보안 측면은 사례 문서에 단편적으로만 있음 (Graphiti 경고, Copilot 적대적 메모리 테스트).
