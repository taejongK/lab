ASCII 맵 NPC 엔진

2D 맵을 ASCII로 그리고, NPC 위치와 오브젝트 설명을 함께 넣은 뒤, System One 모델로 NPC가 어디로 갈지 정하는 로직입니다. 먼저 이 구조가 가능한지 직접 실험으로 평가했고, 그 결과에 맞춰 로직을 설계했습니다.

평가 결론

가능합니다. 단, 역할을 나눠야 합니다. 학습하지 않은 모델에게 ASCII 맵을 주고 상하좌우를 직접 고르게 하면 무작위와 거의 같았습니다. 반면 상황을 보고 “어떤 오브젝트로 갈지” 고르는 의미 판단은 무작위보다 확실히 잘했습니다.

모델이 맡는 것

무엇을 할지. 자극과 오브젝트 설명을 보고 목표 오브젝트(또는 머무르기)를 고른다.

코드가 맡는 것

어떻게 갈지. 맵에서 최단 경로(BFS)를 구하고 그 첫 칸의 방향(상하좌우)을 낸다.

상하좌우를 모델이 직접 고르게 하는 원래 구상은 2단계로 둡니다. 코드가 BFS로 정답 방향을 무한히 만들 수 있으므로, 그 데이터로 모델을 미세조정한 뒤 다시 측정합니다. 게임 데이터로 학습한 사례(PlayJev, NanoJev)는 이 방식으로 성능을 냈습니다.

평가 실험

로컬 Laya 421M(학습 없음, Apple M2)으로 무작위 9×9 맵 60개를 만들어 측정했습니다. 맵에는 벽과 오브젝트 5개(사과, 열쇠, 모닥불, 침대, 우물)가 있고, 각 오브젝트에 설명을 붙였습니다. 스크립트는 probe_ascii_map.py입니다.

  • 한 걸음 정답은 “최단 경로 위의 방향”이면 맞은 것으로 셌습니다. 목표 도달은 최단 거리의 2배 걸음 안에 도착했는지로 셌습니다.
  • B에서 “가까워짐”이라고 써 줘도 방향별 확률이 0.29~0.36으로 거의 균등했습니다. 입력 잘림은 785회 호출 중 0회였습니다. 학습 없는 Laya는 선택지 설명 속 공간 사실을 읽어 쓰지 못합니다.
  • C의 오답은 대부분 “목마름 → 모닥불”, “추움 → 침대”였습니다. 오브젝트 설명에 해결하는 욕구를 더 직접적으로 쓰면 개선될 여지가 있습니다.
  • 응답 시간 중앙값 158ms (M2 CPU/MPS, 상태 약 310토큰).

한계: 맵 60개, 판수 20, 모델 1개(Laya 영어 체크포인트). Jev(호스팅)는 측정하지 않았습니다. 다른 사례 조사와 결론의 방향은 같습니다. NanoJev는 전체 지도로 다음 행동을 바로 고르게 했을 때 Jev와 학습 모델 모두 미로 0/3이었습니다.

한 틱이 도는 모습

아래 맵은 이 문서의 로직을 그대로 돌립니다. 자극을 고르고 “다음 틱”을 누르면 NPC(@)가 한 칸 움직입니다. 오른쪽에는 그 틱에 모델로 보내는 요청이 그대로 나옵니다. 모델 응답 자리는 실험 정답표로 대신했습니다(실제 모델 출력 아님).

이번 틱의 요청 (state + questions)
초록 점(·)은 코드가 계산한 최단 경로입니다.

틱 루프

  1. 자극 수집코드
    이번 틱에 일어난 일을 모읍니다: 욕구 변화(배고픔 증가), 플레이어 접근, 소리, 오브젝트 상태 변화. 자극이 없고 진행 중인 목표가 있으면 모델을 부르지 않고 6단계로 갑니다.
  2. state 만들기코드
    ASCII 맵, 범례, 좌표계 설명, NPC 좌표, 오브젝트 목록(이름·설명·좌표·NPC까지 걸음 수), 자극을 하나의 JSON으로 묶습니다.
  3. 질문 만들기코드
    선택지는 도달 가능한 오브젝트와 stay뿐입니다. 막힌 곳에 있는 오브젝트는 넣지 않습니다.
  4. 판단모델
    System One 모델이 한 번의 forward로 목표 확률분포와 confidence를 돌려줍니다. 텍스트는 생성하지 않습니다.
  5. confidence 게이트코드
    confidence가 기준보다 낮으면 직전 목표를 유지하거나 규칙 기반 기본 행동으로 넘어갑니다. 기준값은 실제 로그로 정합니다.
  6. 경로 계산코드
    현재 위치에서 목표까지 BFS로 최단 경로를 구하고, 첫 칸으로 가는 방향을 up/down/left/right로 냅니다.
  7. 검증 후 적용코드
    그 칸이 벽이 아닌지, 다른 NPC와 겹치지 않는지 확인하고 이동합니다. 목표에 닿으면 상호작용(먹기, 마시기 등)하고 결과를 다음 틱의 자극으로 넘깁니다.
flowchart LR
  E[자극 수집] --> S[state 만들기]
  S --> Q[질문: 목표 오브젝트]
  Q --> M((System One 모델))
  M --> G{confidence 충분?}
  G -- 예 --> P[BFS 경로]
  G -- 아니오 --> H[직전 목표 유지 / 기본 행동]
  H --> P
  P --> V[벽·충돌 검증]
  V --> A[이동 · 상호작용]
  A --> E

데이터 형식

오브젝트

설명은 모델이 의미 판단에 쓰는 유일한 근거입니다. “무엇인지”보다 “NPC의 어떤 욕구·자극을 해결하는지”를 먼저 씁니다.

{
  "symbol": "W",
  "name": "well",
  "description": "Drinking water here removes thirst.",
  "row": 1, "col": 9
}

  "map": ["###########",

  "you": {"row": 5, "col": 4},

{
  "target": {
    "type": "choice",
    "instructions": "Which object should the NPC walk to?",
    "criteria": {
      "apple": "Fresh food. Eating it removes hunger.",
      "well":  "Drinking water here removes thirst.",
      "stay":  "Nothing here helps right now. Stay put."
    }
  }
}

설계 규칙

실험과 사례 조사(Snake, Doom, NanoJev, PlayJev)에서 나온 규칙입니다.

  • 좌표계를 글로 적는다. 행 0이 위인지, up이 행을 줄이는지. Doom 사례들은 각도 부호가 반대여서 NPC가 목표 주위를 빙빙 돌았습니다.
  • 맵만 주지 말고 좌표를 같이 준다. NanoJev 비교에서 좌표와 갈 수 있는 다음 칸을 같이 주자 완주율이 30~55%p 올랐습니다(학습한 모델 기준).
  • 선택지에는 지금 가능한 것만 넣는다. 막힌 방향, 도달 불가능한 오브젝트는 코드가 미리 뺍니다.
  • “아무것도 안 함” 선택지를 넣는다. 없으면 모델은 맞는 답이 없어도 하나를 자신 있게 고릅니다.
  • 경로는 매 틱 다시 묻지 않는다. 목표가 정해지면 코드가 따라갑니다. 매 틱 방향을 물으면 방향이 계속 바뀌었습니다(blocks.ai Doom: 막힘 33회 → BFS로 바꾼 뒤 3회).
  • 시야를 제한하려면 국소 창을 쓴다. NPC 주변 5×5만 ASCII로 보여 주고, 범위 밖 오브젝트는 목록에서 뺍니다(NanoJev Maze 방식).
  • 게임 루프와 모델 호출을 분리한다. 모델이 답하는 동안에도 NPC는 직전 목표를 따라 움직입니다.

단계별 계획

단계모델이 고르는 것확인할 것
1. 엔진 + 목표 선택목표 오브젝트 / stay자극별 목표 정답률, 오브젝트 설명 문구에 따른 차이, confidence 게이트 기준
2. 방향 미세조정up / down / left / rightBFS 정답 수천 개로 Laya를 학습한 뒤 한 걸음 정답률과 도달률을 위 표와 비교
3. 이미지 입력up / down / left / right같은 맵을 타일 이미지로 그려 이미지 입력 모델(Valen류)과 ASCII 비교

남은 위험

  • 목표 선택 정답률 63%는 아직 낮습니다. 오브젝트 설명 문구, Jev, 미세조정으로 얼마나 오르는지 측정해야 합니다.
  • NPC가 여러 명이면 호출 수가 늘어납니다. Laya는 여러 state를 한 번에 처리(predict_batch)할 수 있지만 지연은 측정하지 않았습니다.
  • 목표가 움직이는 경우(플레이어 추적, 도망)는 BFS 목표를 매 틱 갱신해야 합니다. 이번 실험은 고정 오브젝트만 다뤘습니다.
